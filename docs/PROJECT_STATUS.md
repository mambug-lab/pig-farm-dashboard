## 1. 현재 결론

현재 확인된 시스템은 **Google Sheets 원본 일지 → Apps Script 집계 → HTML/JavaScript 대시보드 → GitHub Pages** 구조이다. 초기 Streamlit 시제품을 현재 운영 구조로 기재하지 않는다.

현재 시트의 기준일은 **2026-08-26**이다. 5~8월 원본의 값과 수식을 읽어 지정 입력구간 기준으로 재집계한 결과, 월별 출하·폐사와 누적 예상 MSY **9.66**이 현재 연동 시트와 일치한다. 다만 Apps Script 실행 원본과 자동 트리거의 현재 상태, 실제 브라우저 화면의 정상 연동은 이번 검토에서 확인하지 못했다.

가장 중요한 관리 이슈는 **GitHub의 `apps-script/Code.gs`와 현재 시트 출력 구조의 불일치**이다. 저장소 코드는 날짜 블록 전체 E:H를 검사하고 수동 0을 제외하는 이전 방식이다. Drive의 `code.gs v10.txt`는 원본 E13:H16에서 시작해 39행 간격으로 검사하고 KPI 메타정보를 생성한다. 현재 시트 출력은 이 v10 구조와 일치한다. 따라서 GitHub에 있는 모든 파일이 실제 운영 환경과 동기화되었다고 판단할 수 없다. [G2][D1][S1]

## 2. 판정 원칙

1. 현재 원본 데이터와 재집계 결과를 우선한다.
2. 배포 성공은 해당 커밋의 배포 사실로만 인정한다. 화면의 KPI 정확성까지 입증하지 않는다.
3. 실행 원본을 읽지 못한 경우 백업 코드와 출력 구조의 일치를 근거로 추정하되, 코드 동일성은 미확인으로 남긴다.
4. 과거 문서의 ‘정상’, ‘검증 완료’는 당시 기록으로 보존하며 현재 상태로 자동 승계하지 않는다.
5. 수정안 제공, 파일 생성, 커밋, 배포, 데이터 대조, 사용자 확인을 구분한다. 파일명 버전이나 수정일만으로 정본을 결정하지 않는다.
6. 불일치를 발견하더라도 이 세션에서는 코드나 데이터를 수정하지 않는다.

PM-04의 제외일은 총계행에 재고가 있지만 지정 검사구간이 비어 있어 제외된다. 세 날짜의 출하·폐사는 현재 모두 0이다. 이것이 실제 미입력인지, 지정 구간 외의 작업만 있었던 날인지 이번 검토에서 단정하지 않는다.

## 9. 이 세션의 운영 규칙

- 새 사실은 출처·검토일·커밋 또는 파일 ID·검증 수준과 함께 갱신한다.
- PROJECT_STATUS에는 현재 판단만, CHANGELOG에는 과거 변경 및 근거를 날짜순으로 남긴다.
- 코드 개선 요청은 별도 개발 작업으로 분리하며, 여기서는 변경 필요 사항만 관리한다.
- 문서 수정일, 작업일지 기준일, 커밋 시각, 배포 시각을 혼용하지 않는다.
- 전체 프로젝트 완료율은 산출하지 않는다. 요구사항 전체 목록과 완료 판정이 확정되지 않았기 때문이다.
